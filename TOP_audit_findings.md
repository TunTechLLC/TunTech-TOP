# PHASE 3 — Executive summary

This scoped audit reviewed the TOP backend (services, routers, repositories), the React frontend, and the
`top-deliverable-quality` skill against the code that should enforce it. The goal was to find the **rest of
the defect class** the signal-layer remediation surfaced — silent failures, architecture-rule violations,
data-scoping gaps, missing truncation guards, and skill rules the code doesn't enforce — not to list every
smell. **No Critical (active data-loss) defect remains**: the prior remediation closed the silent
JSON-parse swallow that was losing whole interviews, and `FindingRepository.create()` atomicity holds. What
remains is a consistent *pattern* of **soft-failure surfaces**: broad `except → return default` swallows, a
Rule-2 `bulk_create` landmine that's documented as safe, deliverable-quality rules enforced only by prompt
instruction, no input-size guards before Claude calls, and domain/label constants scattered despite a
canonical home existing. Most are small, localized fixes; their value is closing the *class*, not any one site.

**Finding counts (47 total): Critical 0 · High 13 · Medium 26 · Low 8.**

By category (a finding may touch more than one):
- **Error handling / silent failures:** ~12 — broad `except` swallows in `claude.py` (3 sites), `document_processor` library `pass`, `report_sections` charts + `key_quotes`, `qa_revision` style `pass` + empty-edits ambiguity, `PatternPanel`/`api.js` frontend swallows, `patterns.detect` generic-422.
- **Skill-enforcement gaps (SOFT/NONE where HARD is needed):** 5 — computed≠CONFIRMED, attribution, positive-no-pattern, cross-doc contradictions, ≥2-source / no-generic-praise.
- **Architecture-rule violations:** Rule 2 (`signal.py` bulk_create); Rule 5 ×6 (prompts, report_sections, document_processor, findings/roadmap routers, frontend roadmap statuses).
- **Separation-of-concerns / complexity:** `findings.py` router logic; 2037-line `report_sections.py`; 1790-line `prompts.py`; 1127-line `FindingsPanel.jsx`.
- **Missing truncation guards:** 3 (`document_processor`, `claude`, `qa_revision`) — no shared `MAX_INPUT_CHARS`.
- **DRY:** `claude` fence/array parsing, ~13 `report_sections` table builders, QA prompt boilerplate, router + frontend error handling.
- **Data-scoping:** `read_candidates` path-traversal; unscoped update/accept endpoints; QA/narrator engagement-id trust.
- **Dead code:** `claude` sync client + `re` import; `PatternRepository.accept_contributing`.
- **Async correctness (systemic S1, demoted):** blocking I/O in `async` service methods — near-zero impact for one local user; noted, not prioritized.
- **Missing tests on critical paths:** `_parse_economic_figures`, the (to-be-built) skill-enforcement checks.

## Top 5 systemic issues to fix first

> **Ranking axis = "fix-first" priority: how systemically the issue recurs (many sites, one root cause)
> × its threat to the two things TOP cares about — not silently losing data, and deliverable correctness.**
> This is deliberately *not* strict severity: e.g. #3 (`signal.py` duplicate-ID) is the single most severe
> confirmed defect but ranks third because it's currently dormant (uncalled); strict severity would put it #1.

1. **Silent-failure swallows — finish closing the proven defect class.** Broad `except Exception → return []/None/default` still exists in `claude.py` (`extract_downgrade_recommendations`, `suggest_display_label`, narrator finding-id parse), and log-less `pass`/empty-fallbacks in `report_sections`, `document_processor`, `qa_revision`, and two frontend sites. *Why first:* this is the exact root cause that silently lost a whole CTO interview; each site can turn a transient/parse failure into a confident-but-wrong empty result. Fix = narrow each catch to the expected parse exception, let API/timeout propagate, and `logger.warning` before any legitimate-empty return.

2. **Enforce the deliverable-quality rules in code, not just prompts.** The three HIGH skill gaps — *computed figure must not be CONFIRMED*, *attribution must trace to source*, *Positive finding must carry no pattern* — are SOFT/NONE, so a single model slip ships a mislabeled or mis-attributed client deliverable with no backstop. *Why:* this is a direct continuation of the remediation (the D-label work) and the highest-leverage quality protection. Fix = add deterministic checks in `narrator_auditor.py` + a `valence/pattern` reject in `findings.py`.

3. **Defuse the `signal.py` `bulk_create` Rule-2 landmine.** Verified: it generates duplicate IDs (params built before the single commit) while its docstring certifies the opposite. Currently uncalled, so no live corruption — but it's a loaded gun aimed at the next person who wires up CSV import. *Why:* highest-severity confirmed code defect, ~5-line fix, and the false docstring makes it dangerous. Fix = sequential `_write` loop like `pattern.py` (or delete until needed).

4. **One Claude I/O policy: input-size guard + retries.** No `MAX_INPUT_CHARS` guard precedes any Claude call (oversized transcripts/packets can silently overflow context) and the shared client runs `max_retries=0` (transient 429/5xx become hard failures that the swallows in #1 then hide). *Why:* pairs with #1 to make the Claude layer fail loudly and bounded. Fix = a shared pre-flight size check + non-zero `max_retries` (or one retry wrapper) in `claude.py`, reused by `document_processor`/`qa_revision`.

5. **Finish the centralization refactor (Rule 5).** `prompts.py` already builds `_DOMAIN_LIST` dynamically but then hardcodes the domain list ×5 and the confidence/priority/effort/phase vocabularies; the same drift exists in `report_sections.py`, `document_processor.py`, two routers, and `RoadmapPanel.jsx`. *Why:* these literals silently desync from `domains.py`/`constants.js` and from the validators, reintroducing the labeling-drift problems #2 guards against. Fix = derive all enum prose from `domains.py`/`constants.js`; move `DOMAIN_FILTER_MAP`, `_ANNUAL_DRAG_DOMAINS`, `VALID_PHASES`, `_DOMAIN_AUDIENCE`, `ROADMAP_STATUSES` into the canonical modules.

**Next tier (not top-5, real but lower-stakes for a single-user tool):** extract a `FindingService` out of `findings.py`; split `report_sections.py` (economic parsing / file roles / a generic table builder) and consolidate the ~13 table builders; trim `FindingsPanel.jsx`; add the missing data-scoping guards on update endpoints; add tests for `_parse_economic_figures` and the new enforcement checks. The async-blocking-I/O theme (S1) is acknowledged but intentionally deprioritized given the single-user, local deployment.

# PHASE 2 — Findings by module

## Module 1 — Signal pipeline (`api/services/document_processor.py`)

> The proven defect hotspot from prior remediation. `process_file()`/`process_engagement_files()` are
> declared `async` but do synchronous file + DB I/O — for a single-user tool that is near-zero impact, so
> the event-loop blocking is recorded once under systemic theme **S1**, not as a per-module Critical.

### [HIGH] No truncation/size guard before Claude extraction
- **Location:** `document_processor.py:~649,659-660` — `process_file()`
- **Category:** Missing truncation guards (named defect class)
- **Problem:** File text from `extract_text_from_file()` is passed straight into `_extract_signals_with_retry()` with no length cap. A large transcript/PDF can exceed the context window → silent truncation or a failed call. Exactly the "missing truncation guard" class this audit targets.
- **Fix:** Add a `MAX_DOCUMENT_CHARS` (~50k) guard in `process_file()`; truncate + `logger.warning` when exceeded. Centralize the constant so `claude.py` callers share it.

### [HIGH] Extraction retry covers JSON-parse only, not transient API errors
- **Location:** `document_processor.py:~617-628` — `_extract_signals_with_retry()`
- **Category:** Error handling / Rule 4 (missing retries)
- **Problem:** Retries on JSON-parse failure but not on `anthropic.APIError`/timeout/529; the shared `async_client` is created with `max_retries=0` (Module 2). A transient overload aborts the file (per defect-A it stays unprocessed — safe, but a needless re-run and a quiet gap).
- **Fix:** Catch `anthropic.APIError`/`asyncio.TimeoutError` in the retry loop, OR set non-zero `max_retries` on the shared client (Module 2). One place only — don't duplicate retry logic.

### [MEDIUM] Silent `pass` on malformed signal-library JSON
- **Location:** `document_processor.py:~323-324,331-332` — `_build_library_block()`
- **Category:** Silent failures
- **Problem:** Bad `threshold_bands`/`maturity_levels` JSON in the library is caught and `pass`-ed — the signal definition is injected without bands/levels, silently degrading the extraction prompt with no record of the bad library row.
- **Fix:** Replace `pass` with `logger.warning(... signal_id ... omitting bands/levels)`.

### [MEDIUM] `DOMAIN_FILTER_MAP` hardcoded outside `domains.py` (Rule 5)
- **Location:** `document_processor.py:~21-32` — module level
- **Category:** Rule 5 (centralized domain logic)
- **Problem:** `DOMAIN_FILTER_MAP` couples file-type→domain-subset knowledge to this service; drifts if `VALID_DOMAINS` changes. (`VALID_FILE_TYPES` is legitimately document-specific — leave it.)
- **Fix:** Move `DOMAIN_FILTER_MAP` into `api/utils/domains.py`, import it here.

### [LOW] Error result drops `engagement_id`
- **Location:** `document_processor.py:~922-930` — `process_engagement_files()`
- **Category:** Error handling (observability)
- **Problem:** The per-file error dict omits `engagement_id`, losing traceability when results are aggregated.
- **Fix:** Add `'engagement_id': engagement_id` to the error dict.

_Verified-clean:_ semantic-dedup fallback (`_consolidate_candidates` sets + logs `semantic_degraded` — intentional, no loss); no SQL in this service (Rule 3 OK); extraction routes through `claude.py` (Rule 4 OK); candidate scoping is per-engagement (no cross-engagement leak).

## Module 2 — Claude layer (`api/services/claude.py`)

### [HIGH] `max_retries=0` on the shared async client
- **Location:** `claude.py:~25` — client init
- **Category:** Rule 4 sub-finding (missing retries)
- **Problem:** Every Claude call (all 5 agents + QA + extraction) runs with zero SDK retries, so transient 429/5xx/network blips become hard failures. Combined with the broad `except` swallows below, transient failures masquerade as empty results.
- **Fix:** Set `max_retries=2-3` on `AsyncAnthropic`, OR add one explicit retry wrapper used by all call sites. Single source.

### [HIGH] Broad `except Exception -> return [] / None` swallows transient failures
- **Location:** `claude.py:~369-374` (`generate_report_narrative` finding-ids parse), `~546-575` (`extract_downgrade_recommendations`), `~595-630` (`suggest_display_label`)
- **Category:** Silent failures (core defect class)
- **Problem:** Each catches *all* exceptions (API/timeout/parse alike) and returns a default. Callers can't distinguish "legitimately empty" from "the call failed" — the exact pattern the remediation fixed elsewhere. `extract_downgrade_recommendations` returning `[]` silently drops Skeptic downgrade recommendations on a transient error.
- **Fix:** Narrow to the expected parse exception (`json.JSONDecodeError`/`ValueError`); let API/timeout exceptions propagate (or retry per the finding above). `logger.warning` before any legitimate-empty return.

### [MEDIUM] No input-size guard on unbounded Claude calls
- **Location:** `claude.py` — `extract_signals_from_transcript`/`extract_signals_from_document`/`call_claude`/narrator/finding/roadmap extractors
- **Category:** Missing truncation guards
- **Problem:** Case packet / transcript / synthesizer output are interpolated without any size check; oversized input can blow the context window and fail or silently degrade. (Shares root with Module 1 guard.)
- **Fix:** One shared pre-flight check (`MAX_INPUT_CHARS`) raising a clear `ValueError`, reused by all long-input functions.

### [MEDIUM] Duplicated fence-strip / JSON-array extraction scaffolding (DRY)
- **Location:** `claude.py` fence strip at `~114-120,196-203,530-537`; bracket extraction at `~204-207,538-541` (duplicates `_parse_json_array`)
- **Category:** DRY
- **Problem:** Markdown-fence stripping is copy-pasted in 3 functions; array-bounds extraction in 2 more, duplicating canonical `_parse_json_array`. Fixing parsing in one place misses the others.
- **Fix:** Extract `_strip_fence_wrap(text)` and route all array parsing through `_parse_json_array`.

### [LOW] Dead synchronous client + unused `re` import
- **Location:** `claude.py:~24` (`client = anthropic.Anthropic(...)` never used), `~2` (`import re`, single use)
- **Category:** Dead code
- **Problem:** A sync client is instantiated but never called — a foot-gun against Rule 1 if a future edit reaches for it.
- **Fix:** Delete the sync client; drop `import re` once fence-strip is unified.

_Verified-clean:_ all calls use `async_client` (Rule 1 OK); no SQL (Rule 3 OK); single Claude entry point (Rule 4 OK); no hardcoded domains (Rule 5 OK); long calls stream via `_stream_final_message`; `_parse_json_array`/`_parse_narrator_json` correctly raise. (The agent's "non-streaming small call" and "timeout-comment" items are PASS — small `max_tokens` calls intentionally don't stream.)

### [MEDIUM] Path-traversal: `read_candidates` opens an arbitrary `file` param unscoped
- **Location:** `signals.py:88-98` — `read_candidates()`
- **Category:** Data-scoping / input validation
- **Problem:** `file` (query param) is passed straight to `os.path.exists`/`open` with no check that it lives under the engagement's candidates folder; `engagement_id` is accepted but unused. ### [MEDIUM] Update/accept endpoints don't verify the record belongs to the engagement

### [MEDIUM] Hardcoded domain/phase constants in routers (Rule 5)

## Module 7 — Repositories (`api/db/repositories/`, all 19) + `ids.py`

### [HIGH] `SignalRepository.bulk_create` violates Rule 2 — and its docstring falsely certifies it safe
- **Location:** `signal.py:127-161` — `bulk_create()`
- **Category:** Rule 2 violation / latent data corruption
- **Problem (verified in source):** The method builds the full `params` list calling `next_signal_id()` for **every** row (lines 140-158) **before** the single `_write_many()` commit (line 161). Because `next_signal_id()` is MAX+1, every row reads the same MAX → **duplicate IDs** — exactly the failure the docstring (lines 134-137) claims to prevent ("Sequential loop commits each ID before the next call reads the new MAX"). The code does the opposite of its docstring. `pattern.py:104-113` is the correct reference pattern (`next_ep_id()` then `_write()` inside the loop). **Blast radius:** grep confirms `SignalRepository.bulk_create` is currently **never called** (the live load path `load_candidates` uses per-signal `repo.create()`), so this is a *loaded gun*, not active corruption — but it's a Rule-2 violation with a docstring that will mislead whoever wires up the "Tally CSV import" it was written for.
- **Fix:** Replace the params-list + `_write_many` with a sequential loop: `for row in rows: self._write(INSERT_SIGNAL, (next_signal_id(), ...)); count += 1` — mirror `pattern.py`. (Or delete the method until CSV import is actually built.)

### [MEDIUM] Dynamic SET-clause from field names in `update_settings`
- **Location:** `engagement.py:131-134` — `update_settings()`
- **Category:** Data access (SQL construction)
- **Problem:** SET clause is built by interpolating `fields.keys()` into the SQL string. Values are parameterized (`?`) — safe today because the keys come from a 4-field Pydantic model (`EngagementSettingsUpdate`), but the pattern invites injection if a future field is sourced from user input.
- **Fix:** Map allowed model fields → fixed column names via an explicit dict literal; interpolate only from that allowlist.

### [MEDIUM] N+1 in `validate_prerequisites`
- **Location:** `agent_run.py:131-141` — `validate_prerequisites()`
- **Category:** Data access (N+1)
- **Problem:** Loops `required_agents` calling `get_accepted_output()` once per agent (5 queries where 1 `IN (...)` would do). Single-user lowers urgency.
- **Fix:** One query `... WHERE engagement_id=? AND agent_name IN (?,?,...) AND accepted=1`, then diff against required.

### [LOW] Dead method `PatternRepository.accept_contributing`
- **Location:** `pattern.py:118-126`
- **Category:** Dead code
- **Problem:** Docstring says "Called by FindingRepository.create()" but it isn't — finding atomicity is handled inline via `_write_transaction()`. The stale docstring creates a false mental model.
- **Fix:** Delete it, or wire it in and test it. At minimum fix the docstring.

_Headline checks:_ **Rule 2 — every OTHER `bulk_create` uses a correct sequential loop** (`pattern.py`, `qa_coverage/coherence/editorial/revision.py`, `signal_coverage.py`) — only `signal.py` violates it. **`FindingRepository.create()` is atomic** via `_write_transaction()` (Rule preserved ✅). All repos inherit `BaseRepository`; no repo opens SQLite directly; all query *values* are parameterized with `?`. No silent DB-error swallows found.

## Module 9 — Skill enforcement cross-check (`top-deliverable-quality` vs. code)

> The named defect class includes "a skill-rule the code didn't enforce." This module maps each load-bearing
> skill rule to HARD (deterministic code check), SOFT (prompt instruction only — a model slip ships), or NONE.
> Findings below are from the cross-check agent's read of `SKILL.md` + the prompts/auditors; the *enforcement
> level* is the finding, and each fix is a concrete deterministic backstop.

| Skill rule | Enforcement | Priority |
|---|---|---|
| Four confidence labels only | SOFT (prompts) | — |
| **Computed figure must NOT be CONFIRMED** | **SOFT** | **HIGH** |
| **Attribution: person + exact title traces to source** | **NONE** | **HIGH** |
| Negative/Dual finding → ≥1 pattern | **HARD** (`findings.py:339-344`) | — |
| Positive finding → ≥1 Strength signal | HARD (`findings.py:328-338`) | — |
| **Positive finding → 0 patterns** | **SOFT** (prompt only; not rejected in code) | **HIGH** |
| Cross-document contradiction detection | SOFT | MEDIUM |
| Documented pattern = ≥2 independent sources | SOFT | MEDIUM |
| Generic praise invalid (Positive needs specifics) | SOFT | MEDIUM |
| CONFIRMED opportunity only if validated | SOFT | LOW |
| Economic range logic defensible | NONE | LOW |

### [HIGH] Computed economic figures can be labeled CONFIRMED with no code backstop
- **Skill rule:** "A calculation on CONFIRMED inputs produces ESTIMATED/DERIVED — never CONFIRMED" (SKILL.md Step 2/6; the "BRIGHT LINE", `ECONOMICS_PROMPT` ~97-99).
- **Enforcement:** SOFT — prompts only. `narrator_auditor.check_economic_figures_grounded` (~245) checks figures are labeled / match DB, **not** that the label matches the figure's derivation.
- **Problem:** This is the exact remediation theme (D label refinement). A model slip relabeling a computed overrun as CONFIRMED ships to the client with nothing to catch it — the precise E004 "$483K leakage labeled CONFIRMED when it was rate×hours" failure.
- **Fix:** Add a deterministic check in `narrator_auditor.py`: for each economic figure labeled CONFIRMED, scan the surrounding prose for derivation markers (`×`, `*`, `+`, "per", "times", "calculated", "derived from", a `$×number×number` shape) → FAIL with the figure + label. Mirrors the prompt's bright line.

### [HIGH] Positive (Preserve) findings are never rejected for carrying a pattern
- **Skill rule:** "A Preserve finding has **no** contributing pattern (the library is a dysfunction catalog); it traces to ≥1 Strength signal" (SKILL.md Step 5).
- **Enforcement:** SOFT/asymmetric — `findings.py:328-338` enforces the *Strength-signal* half (HARD) but nothing rejects a `valence=='positive'` finding that *also* has `contributing_ep_ids`.
- **Problem:** A positive finding mistakenly tied to a pattern conflates strength-preservation with dysfunction diagnosis and renders mixed evidence — the prompt forbids it but code accepts it.
- **Fix:** In `findings.py` create/parse: `if valence=='positive' and contributing_ep_ids: raise HTTPException(... "Preserve finding cannot have contributing patterns")`. (Verify the exact field name during implementation — this is from the cross-check's read, not independently confirmed.)

### [HIGH] Attribution (named person + exact title ↔ source) has zero enforcement
- **Skill rule:** "Verify every named person/role: correct person, exact title, correct context" (SKILL.md Step 3).
- **Enforcement:** NONE. `narrator_auditor.check_no_individual_names` (~450) only *suppresses* names in risk tables; it never verifies that a named person/title actually appears in a loaded source.
- **Problem:** A mis-attributed role (the E004 "Jennifer Torres (CFO)" vs. real "Sandra Okafor, Director of Operations") ships with no backstop.
- **Fix:** Heuristic check in `narrator_auditor.py`: extract person+role mentions from the narrative; FAIL if a person name doesn't appear in any `ctx.processed_files` text. Catches obvious mismatches even if imperfect.

### [MEDIUM] No cross-document contradiction detector (dates/figures/status)
- **Skill rule:** Step 4 — flag date/figure/status conflicts across documents, don't resolve silently.
- **Enforcement:** SOFT — extraction prompt does a within-document scan; nothing compares values across loaded documents post-extraction. (This is the BACKLOG "Decision Surfacing" item — confirms it's a real, currently-unenforced gap.)
- **Fix:** A `check_date_figure_consistency` auditor: bucket ISO dates / dollar figures across `processed_files` by a coarse key; FAIL when one key holds >1 distinct value.

### [MEDIUM] "Documented pattern = ≥2 sources" and "no generic praise" are prompt-only
- **Skill rule:** Step 7 — High pattern needs ≥2 independent sources; Positive strengths must name a specific account/metric/behavior.
- **Enforcement:** SOFT for both.
- **Fix:** Auditor check counting unique signal codes per accepted pattern vs. its confidence label; regex check flagging vague-praise titles ("strong/great/excellent team") on Positive findings lacking a specific noun/metric.
